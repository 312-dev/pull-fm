# Phase 8 security audit, Gate 8

**Date:** 2026-07-29
**Scope:** the whole backend as it exists at commit `724810a`, plus the CI gates that guard it.
**Method:** threat-model review against the shipped architecture, adversarial verification of the
claims that would be most expensive to have wrong, supply-chain audit of the lockfile, and a
defect hunt through the CI gates themselves.

---

## Verdict: Gate 8 FAILS

Gate 8 (`docs/PLAN.md` section 7) has three clauses. Two of them are not met, and one of them was
being reported as met by a scanner that was not looking.

| Clause                                                              | Status                 | Why                                                                                                             |
| ------------------------------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| Zero high/critical from **Semgrep**                                 | **PASS**               | 0 findings at ERROR after the rule fixes below. The WARNING rule was never evaluated at all; that is now fixed. |
| Zero high/critical from **Trivy**                                   | **FAIL**               | 1 CRITICAL and 2 HIGH in `pnpm-lock.yaml`, all with published fixes. Previously invisible. See F1.              |
| Zero high/critical from **gitleaks**                                | **PASS**               | Clean over 94 commits after two allowlist defects were closed. See F4, F5.                                      |
| Zero high/critical from **ZAP baseline**                            | **FAIL, never run**    | There is no DAST job in any workflow. `security/zap/` is written, tested by hand, and wired to nothing.         |
| **Pinned tool versions**                                            | **PASS**               | All 21 action and image references pinned. The checker that proves it had two bypasses; both closed. See F7.    |
| Every accepted risk has an **owner and expiry**, CI fails on expiry | **PASS, now honestly** | 9 valid entries. The validator could be silently emptied two different ways; both closed. See F6.               |
| **Observatory >= A+**                                               | **FAIL, unmeasurable** | The staging origin answers 521. An Observatory grade against a Cloudflare error page measures nothing.          |

**The gate cannot pass today.** The two hard blockers are the dependency finding, which is a
one-line remediation deliberately not taken tonight (see F1), and the complete absence of any DAST
execution, which needs a deployed target that does not currently exist.

Nothing in this report argues that the system is insecure. The security engineering here is
genuinely above the level this project's size would predict: envelope encryption with AAD binding
that resists row-swapping, a magic-link-only auth surface with no password to steal, a sealed
cookie that is a transport rather than a second identity, and an auto-generated BOLA suite. Every
one of those held up under direct attack. What failed is the layer that is supposed to _prove_
those things keep holding.

## The through-line: the gates were weaker than the code they guard

This project already knows this failure mode. Three prior instances are recorded in its own
comments: a Semgrep regex whose window closed too early, a `--error` with no severity filter that
made a WARNING block the build, and a gitignored ruleset that meant CI looked configured and
scanned nothing.

**Every high-severity finding in this audit is another instance of it.** Not one is a flaw in the
application's security design. All nine are a check that reports success while not checking.

That is worth naming because it changes what to do about it. The remedy is not more rules. It is
that a security check must fail when it cannot do its job, and several here treated "found nothing"
and "looked at nothing" as the same answer:

- Trivy printed `0` because it suppresses dev dependencies by default.
- The action-pinning lint printed `OK 0 references pinned` when its regex matched nothing.
- The register validator treated an empty register as valid, so anything that emptied it passed.
- The DAST spec pruner exits 0 on a spec with zero operations, which is what ZAP would then scan.

Four different tools, one bug.

## Findings

Severity is the impact if the finding is exploited or relied upon, not the difficulty of fixing it.
"Proved" means I ran it and observed the result. "Reasoned" means I read the code and believe it.

### HIGH

#### F1. The dependency gate was blind to every advisory this repository actually has

**Proved.** `.github/workflows/security.yml`, `deps` job.

Trivy suppresses development dependencies unless told otherwise. Running the CI invocation verbatim:

```
trivy fs . --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed
  -> pnpm-lock.yaml | pnpm | 0        exit 0, gate PASSES
```

Adding one flag:

```
  -> Total: 3 (HIGH: 2, CRITICAL: 1)
     vitest          2.1.9   CVE-2026-47429  CRITICAL  fixed in 3.2.6, 4.1.0
     vite            5.4.21  CVE-2026-53571  HIGH      fixed in 6.4.3, 7.3.5, 8.0.16
     brace-expansion 1.1.16  CVE-2026-14257  HIGH      fixed in 5.0.8
```

100% of this repository's advisories are dev dependencies, so the default suppression removed 100%
of them. Gate 8's wording, "zero high/critical from Trivy", was satisfied only because Trivy was
not looking. There is also no `pnpm audit` step anywhere, and no Dependabot or Renovate config, so
nothing proposed the bump either. The weekly re-scan faithfully re-ran the same blind check.

**Exploitation.** THREAT-MODEL T27, the only CRITICAL in the supply-chain boundary. Dev
dependencies are not inert: `pnpm test` runs vitest in CI against a checked-out tree with a
`GITHUB_TOKEN` in the environment. CVE-2026-47429 is arbitrary code execution via path traversal.
The realistic path is not a drive-by; it is that "we scan dependencies and the gate is green" is
load-bearing in the threat model, and it was false.

**Fixed:** `TRIVY_INCLUDE_DEV_DEPS: "true"` on the scan, plus a `pnpm audit --audit-level high`
step as an independent second opinion on the same lockfile.

**NOT fixed, and this is the gate blocker:** the versions themselves. The remediation is a single
coordinated `vitest` bump to `>=3.2.6` across four workspace packages, which also resolves the
`vite` and `esbuild` chain, plus an `eslint` bump or a pnpm override for `brace-expansion`. That is
a **major version upgrade of the test runner**, and landing one unattended at 03:00 in a tree three
other agents are actively writing to is how you turn one finding into a morning of archaeology. The
gate is now correct and red; the bump should be a deliberate change with the suite watched.

#### F2. The BOLA Semgrep rule was never evaluated, in any invocation, anywhere

**Proved.** `.semgrep/pullfm.yml:57`, `.github/workflows/security.yml:72`.

`pullfm-bola-missing-owner-predicate` is authored at `severity: WARNING`, and the CI step passes
`--severity=ERROR`. The comment above that step explains the choice carefully: the rule is "a
WARNING tripwire, not a gate".

`--severity` does not down-rank a rule. It removes it from the run:

| invocation                       | Rules run | findings                                                 |
| -------------------------------- | --------- | -------------------------------------------------------- |
| `--severity=ERROR` (what CI did) | 6         | 3                                                        |
| no severity filter               | 7         | 5, including the BOLA rule on `SELECT ... WHERE id = $1` |

`package.json`'s `scan:sast` uses the same filter, so there was no invocation in the repository
that would have surfaced it. A tripwire that is never evaluated and prints nowhere is dead code.

This is the same defect as the incident the comment describes, resolved in the opposite direction:
the first time the rule blocked when it should have reported, this time it vanished when it should
have reported.

**Fixed:** a second, non-blocking `semgrep scan --config=.semgrep/ --severity=WARNING` step. No
`--error`, so it reports without gating, which is what "tripwire" meant all along.

#### F3. `schema: { hide: true }` removes a route from the entire Gate 3 chain, silently

**Reasoned, with a live instance confirming the mechanism.** `apps/bff/src/lib/openapi.ts:91`.

```ts
if (schema?.hide === true) return; // collectAnnotations
```

Gate 3 says the BOLA suite "enumerates every user-scoped route from the OpenAPI spec ... failing CI
if any route lacks a test". One property defeats the whole chain, at four consecutive links:

1. `collectAnnotations` returns before reading the annotation, so the route is never classified.
2. Being absent from the swagger document, `applyAnnotations` never adds it to `unclassified` and
   never throws. The deliberate refusal to emit an unclassified operation is bypassed by not being
   an operation.
3. `openapi.test.ts` filtered hidden routes out of its inventory assertion.
4. So the route is absent from the route matrix, and the BOLA suite generates zero tests for it.

The escape is live, not theoretical: `plugins/docs.ts:132` registers `GET /openapi.json` with
`hide: true` and no annotation, and the emitter does not complain. That is the proof that the path
works end to end. Contrast the sibling branch two lines later (`raw === undefined -> return`),
which _is_ caught downstream. `hide` is the only unguarded exit.

**Exploitation.** A developer adds an internal or admin-ish route, marks it hidden because it is
not for public documentation, and ships a user-scoped route with no authorization test and a green
build. This is not adversarial; it is the ordinary reason someone writes `hide: true`.

**Guarded, not closed:** an allowlist test in `openapi.test.ts`. The set of hidden routes must
equal exactly `{GET /openapi.json}`; any new hidden route fails CI with an explanation, and a stale
allowlist entry also fails. The escape is not removed because a hidden route is sometimes correct
(the spec cannot describe itself), but it is now loud. **The stronger fix, recommended:** make
`collectAnnotations` require a hidden route to carry an explicit annotation rather than skipping it,
so the classification is written down at the route rather than in a test file.

#### F4. The gitleaks path allowlist exempted exactly the files that receive real credentials

**Proved.** `.gitleaks.toml`, path allowlist.

Two entries were far wider than their description:

```
'''(^|/).*\.example$'''    matches .env.example and all four terraform.tfvars.example
'''(^|/)docs/.*\.md$'''    matches every markdown file under any docs dir at any depth
```

I put an identical, valid-format `sk_live_...` key plus a Hetzner-shaped token into four paths and
ran the repository's own command:

| file                                                 | findings  |
| ---------------------------------------------------- | --------- |
| `apps/bff/src/leak.ts`                               | 3, exit 1 |
| `.env.example`                                       | **0**     |
| `docs/runbook.md`                                    | **0**     |
| `infra/terraform/envs/prod/terraform.tfvars.example` | **0**     |

**Exploitation.** A `terraform.tfvars.example` exists to be copied and filled in with a real
Cloudflare, Hetzner, or WorkOS token. The single most likely way a credential enters this repository
is someone editing the example instead of the copy, or pasting a working `curl -H "Authorization:
..."` into a runbook while debugging. Both were exempt. The repository is public, so a leaked
credential is compromised the moment it is pushed, which is the reason `security.yml` runs the
secret scan first and fails fast. `.env.example:9` asserted "gitleaks blocks any commit containing
one"; for that file it did not.

**Fixed:** both path entries removed. Neither is replaced by a narrower path rule, because there is
no path whose future contents can be promised. The two genuine documentation sample tokens are
allowlisted **by value** instead, which is the right mechanism: a different token in the same file
is still a finding, and value scoping survives the fact that gitleaks scans full history where a
doc edit cannot retract what an old commit contains.

#### F5. The `xxxx+` stopword suppressed any secret containing four consecutive x characters

**Proved.** `.gitleaks.toml`, global allowlist regex.

`xxxx+` sat in a `regexTarget = "match"` allowlist, so it matched anywhere inside the rule's match
region, not just as a standalone placeholder:

The probe was a `sk_live_` prefix, then `xxxx`, then 35 further base62 characters, in a source file
with no path exemption. The literal is deliberately broken up here rather than quoted whole,
because this repository is public and the scanner is now correct enough to flag it, which is the
finding demonstrating itself:

```
"sk_live_" + "xxxx" + <35 base62 chars>   with xxxx+ allowlisted  ->  0 findings
the identical string, xxxx+ removed       ->  workos-api-key AND
                                              stripe-access-token both fire
```

A four-character run inside a base62 secret is not exotic. Over a 43-character key space it is a
one-in-a-few-hundred-thousand event, against a generator this service runs constantly. Combined
with F4 the two allowlists overlapped: the documentation token `pfm_live_xxxxxxxx...` was suppressed
twice over, which is why neither defect had ever produced a visible symptom.

**Fixed:** removed. `REPLACE_ME`, `CHANGEME`, `YOUR_..._HERE` and the rest are kept, because no real
credential contains them.

#### F6. The accepted-risk register could be emptied two different ways, at exit 0

**Proved.** `security/scripts/check-accepted-risks.mjs`.

Gate 8's second clause is this register. Both defects produce the worst available outcome for a
gate: not a missed finding, but an affirmative claim that every accepted risk is valid when none
was read.

**(a) Duplicate top-level key.** Root keys were assigned with `root[key] = []` and no duplicate
detection, although indent-4 duplicates _were_ rejected. One extra line `register:` anywhere at
indent 0 replaced the parsed list with an empty one:

```
control (an entry expired 2401 days ago):  FAIL, exit 1
+ one line "register:":                    OK  0 accepted risk(s) valid, exit 0
```

**(b) An early `---`.** `extractFrontmatter` closes at the first line whose trim is `---`. In a
markdown file a bare `---` renders as a horizontal rule, so it reads as formatting in review.
Inserting one before the third entry discarded 7 of 9:

```
control:                     FAIL, exit 1
+ "---" before entry 3:      OK  2 accepted risk(s) valid, exit 0
```

Neither was caught because zero entries is an explicit pass, and the self-test suite codifies that
("an empty register passes"). That is a defensible rule on its own and it is what made both
defects silent.

**Fixed:** duplicate top-level keys are rejected, and the closing fence is validated by counting
`- id: PULLFM-RISK-` markers in the whole file against those inside the frontmatter. The count check
is format-independent and cannot be defeated by moving the fence, because the orphaned entries are
still in the file being counted. Two fixtures and two self-tests added; the suite is 19 tests, all
passing.

#### F7. The action-pinning lint missed two ordinary YAML shapes, and reported success on zero

**Proved.** `security/scripts/check-action-pinning.mjs`.

The pattern required `uses:` at token start with the value on the same line. Both of these are
valid YAML that GitHub Actions accepts, and both were invisible:

```yaml
- { uses: attacker/action@main } # flow style
- name: evil
  uses: attacker/action@main # value on the next line
```

Worse than missing them: because `checked` stayed at 0, the run printed
`OK 0 action/image reference(s) pinned` and exited 0. The script guarded against an empty
_directory_ but not an empty _parse_, so "my regex stopped matching real workflow syntax" was
indistinguishable from "everything is pinned".

**Exploitation.** THREAT-MODEL T29. A mutable tag can be repointed by whoever controls the upstream
namespace, and that code runs inside a workflow that has already checked out our source. The lint
exists because `PULLFM-RISK-002` was retired on the promise that a guard would prevent regression;
the guard had two doors.

**Fixed:** both shapes matched, and zero-references-checked is now a failure with an explanation.
The real repository still passes at 21 references.

#### F8. MusicBrainz rate-limit enforcement is bypassable three ways, one of which looks like correct code

**Proved.** `.semgrep/pullfm.yml`.

MusicBrainz permits 1 request per second for the entire service, per IP, and revokes without appeal.
`PLAN.md` section 8 calls exceeding it product-ending. The Semgrep rule guarding it required the
host as a literal inside the first string argument to `fetch`. I wrote four call sites and scanned
them with the project ruleset. Only the fourth was caught:

```ts
fetch(`${MUSICBRAINZ_BASE_URL}/artist/${mbid}`); //  NOT caught (constant is exported)
const HOST = "musicbrainz" + ".org"; //  NOT caught (host assembled)
new ProviderClient({ name: "musicbrainz", baseUrl: MB }); //  NOT caught, and NO rate limiter
fetch("https://musicbrainz.org/ws/2/artist/x"); //  caught
```

**The third is the dangerous one**, because it looks like using the sanctioned abstraction.
`rateLimiter` is optional on `ProviderClientOptions` (`provider-client.ts:105`), so a second
MusicBrainz client with no pacing compiles, type-checks, passes review, and doubles the egress rate.
Nothing in the type system objects.

**Exploitation.** AT-5, quota arson, except the attacker is us. A developer adds a MusicBrainz
lookup to a new service, constructs a `ProviderClient` because that is the house pattern, forgets
the limiter because it is optional, and the service is blocked with no appeals process.

**Fixed:** three rules now. Host-in-a-literal (widened to the whole call, plus concatenated hosts),
`MUSICBRAINZ_BASE_URL` used outside the sanctioned client, and a `ProviderClient` aimed at
MusicBrainz with no `rateLimiter`. Verified: all four bypasses caught, and a legitimate client
carrying a limiter plus an attribution object referencing the host produce zero findings.
**Stronger fix, recommended:** make `rateLimiter` structurally required when `name` is
`"musicbrainz"`, so the type system enforces the licence condition rather than a lint.

#### F9. The background-job schedule check is satisfied by commented-out lines

**Proved by a subagent, not fixed.** `infra/scripts/check-job-schedule.mjs:286`.

The check asserts each job is enabled via `bootstrap.includes(...)`. Prefixing all four enable
lines with `# DISABLED FOR NOW:` still produces
`PASS: every job is scheduled, enabled, bounded`, exit 0. The same weakness appears at three other
places in the file (installer lines, runner lines, and runbook quotes, where a section headed
"wrong, do not use" satisfies the quote check).

The script's own header names precisely this failure: "installed-but-not-enabled is the same failure
as not-scheduled-at-all, and it looks like progress in a diff". A substring test cannot see the
difference. These jobs enforce the retention windows the privacy policy publishes, so a silently
disabled one is a compliance gap (Gate L), not only an operational one.

**Not fixed:** `infra/` is out of this pass's scope. The fix is to strip comment lines before the
`includes` test, which is a few lines.

### MEDIUM

#### F10. All three origin ingress layers reduce to "any Cloudflare customer", and the config says otherwise

**Reasoned.** `infra/staging/app/nginx-pullfm.conf.in:48-50,148-154`.

The origin now answers 443 on its public interface, behind three controls that are documented as
independent:

1. Hetzner firewall: inbound 80/443 from Cloudflare ranges only.
2. nginx allowlist on `$remote_addr` against Cloudflare's published ranges.
3. Authenticated Origin Pulls (mTLS), plus a subject check.

Layers 1 and 2 are the same predicate expressed twice: "the peer is a Cloudflare edge address".
Cloudflare's edge is shared by every Cloudflare customer, so neither distinguishes our zone.

Layer 3 is meant to fix that, and the configuration says so:

```
#   4. Authenticated Origin Pulls uses a CA shared by every Cloudflare
#      customer, so `ssl_verify_client on` alone proves only that the peer is
#      *someone's* Cloudflare. The subject check closes that gap.
```

**It does not close that gap.** Zone-level AOP presents a single shared certificate, identical for
every Cloudflare customer, whose subject is `CN=origin-pull.cloudflare.net`. Requiring that subject
is therefore exactly as strong as requiring the issuer: it proves "somebody's Cloudflare", which is
the thing the comment correctly identifies as insufficient. The reasoning is right and the remedy
does not follow from it.

**Exploitation.** An attacker who learns the origin IP (historical DNS, certificate transparency,
any outbound connection from the box; THREAT-MODEL T01 already assumes this) creates a free
Cloudflare zone, points a proxied A record at the origin, and sends requests with the right `Host`.
Cloudflare's edge performs the origin pull with the shared AOP certificate, and all three layers
pass. They reach the BFF directly, bypassing our zone's edge entirely.

**What that bypass is worth is smaller than it sounds today, and larger tomorrow.** See F11: our
zone currently has no WAF and no rate-limiting rules, so there is very little at the edge to bypass.
Combined with F12 it means an attacker who knows the origin IP faces no effective per-IP rate limit
anywhere in the stack. It also bypasses the Cloudflare maintenance worker, which Gate 6 depends on.

**Recommended fix**, in order of preference: per-hostname Authenticated Origin Pulls with a
certificate we generate (this is the control that actually distinguishes our zone), or a
high-entropy shared header injected by a Cloudflare Transform Rule and required by nginx. Either is
cheap. **This belongs in `accepted-risks.md` if it is not fixed**, and I have deliberately not added
an entry, because accepting a risk is the operator's decision and not the auditor's.

#### F11. There is no Cloudflare WAF or rate limiting, while several documents describe them as the outer layer

**Proved by absence.** `infra/terraform/modules/zone-settings/main.tf`.

The zone-settings module creates seven resources: `ssl`, `always_use_https`, `min_tls_version`,
`tls_1_3`, `automatic_https_rewrites`, `security_header`, `authenticated_origin_pulls`. There is no
`cloudflare_ruleset` anywhere in `infra/terraform`, so there are no WAF rules, no rate-limiting
rules, and no bot management in code.

Meanwhile `infra/terraform/envs/*/main.tf:132` warns that a misconfiguration "hands an attacker a
direct path around WAF and rate limiting", THREAT-MODEL T01 describes bypassing "WAF, bot
management, per-IP rate limits, and the maintenance worker in one move", and `M24`'s status is
`spec`. The threat model is describing the intended design; the tree contains the TLS half of it.

This is not a vulnerability by itself. It matters because F10 and F12 are both scored on the
assumption that something sits in front, and nothing does.

#### F12. The only per-IP rate limiter is a 5,000-entry in-process LRU, and IP rotation resets it

**Proved.** `apps/bff/src/server.ts:199`, `@fastify/rate-limit` `LocalStore`.

`rateLimit` is registered with no `redis` option, so it uses the default `LocalStore`: an in-process
LRU with a default capacity of 5,000 entries. Driving the exact registration from `server.ts`:

```
A: hits 1-4 (max=3)                      200 200 200 429
A: is it latched at 429?                 429
distinct rotating source addresses       5600
A: hits again after the rotation         200 200 200 429     <- full budget restored
```

An attacker who interleaves one request from each of 5,000-plus addresses evicts their own throttled
counter and starts again. With IPv6 this is free: a single /64 provides more addresses than the
cache can hold, and Cloudflare forwards the full client v6 address.

**This is THREAT-MODEL T11 wearing different clothes.** T11 is "rate-limit counters evicted under
cache pressure, silently disabling rate limiting", and the two-Redis-instance design exists
specifically to prevent it. That design does not apply here, because the global limiter is not in
Redis at all. The comment at `server.ts:179` reassures the reader that per-token budgets live in the
`noeviction` instance "so it cannot be silently disabled by cache pressure", which is true of the
per-token limiter and says nothing about the one being configured immediately below it.

The counters are also lost on every container swap, and `pullfm-deploy.timer` fires every 60
seconds.

**Recommended fix:** point the global limiter at the quota Redis (`RedisStore`), which is the store
the architecture already built for exactly this and already fails closed. Alternatively raise
`cache` far above any plausible distinct-IP count and accept the memory, but that only moves the
threshold.

#### F13. The strongest credential has no per-credential budget; only the weakest does

**Reasoned.** `apps/bff/src/plugins/auth.ts`.

`enforceTokenRateLimit` applies to personal API tokens, which are read-only, scoped, cannot mint
another token, cannot manage connections, and cannot delete the account. Session credentials, which
hold every scope and every irreversible operation, get no per-credential limit at all: only the
global per-IP floor from F12, which F12 shows is defeatable.

The comment explains that the global limiter runs at `onRequest` before the subject is known, which
is correct. But `requireAuth` runs at `preValidation` and _does_ know the subject, and that is where
the per-token budget already lives. Extending it to sessions is the same code path.

**Exploitation.** One authenticated session, rotating source addresses, can drive
`GET /v1/tracks/:mbid/preview` without bound. That route resolves Deezer live on the request path
(signed URLs expire and cannot be cached). The consequence is bounded by the client-side
`QuotaCounter` (Deezer 40 per 5s, iTunes 15 per minute), so the provider is protected and the harm
lands on legitimate users as a denied preview rather than on the vendor relationship. That is the
design working. It still means one account can deny previews to all accounts.

#### F14. Every upstream limiter is per-process, and Terraform's scale guard says otherwise

**Proved by absence.** `packages/upstream` has no Redis dependency of any kind for pacing.

The MusicBrainz `RateLimiter`, the Deezer and iTunes `QuotaCounter`s, and the global per-IP limiter
are all in-memory, per-process objects. At `app_node_count = 1` that is correct and Gate 1's
"<= 1.0 req/s measured at the network layer" holds.

The Terraform variable that guards scaling says this:

> `enable_cache_node` ... MANDATORY before `app_node_count` goes above one, because the MusicBrainz
> token bucket lives in Redis and the 1 req/s ceiling is global to the service.

**There is no Redis token bucket.** Provisioning the cache node would not make the limiter shared.
So the plan-time guard offers an operator a specific, false assurance at exactly the moment they are
making the change that breaks a licence condition, and Gate 1's measurement would keep passing on
each node individually while the egress at the shared IP doubled.

**Recommended fix:** either implement a Redis-backed limiter before the second node exists, or
correct the variable description now so the guard tells the truth. The second is five minutes and
should not wait for the first.

#### F15. Staging deploys code that has not passed either gate

**Reasoned.** `.github/workflows/deploy-staging.yml`.

The deploy workflow triggers on `push: branches: [main]` with no `needs:` on `ci` or `security`, and
no workflow-level gating. All three workflows start in parallel; the image is pushed to ghcr and
`pullfm-deploy.timer` polls every 60 seconds. Staging can be serving code whose secret scan or SAST
run is still in flight, or has already gone red.

Given that `security.yml`'s own header explains that the secret scan "must gate the merge, not
merely report on it", running the deploy beside it rather than behind it undercuts the stated
intent.

#### F16. Two spec-driven gates produce a confident green on zero input

**Proved by a subagent.** `security/bola/route-matrix.mjs`, `security/zap/scripts/prune-openapi.mjs`.

- Downgrading every `x-pullfm-authz: user-scoped` to `authenticated-shared` and dropping the
  `x-pullfm-bola` block yields `operationCount 27, bolaTestCount 0`, exit 0. The classification is
  authored by the same pull request that adds the route, and nothing cross-checks it against handler
  behaviour. The only floor is `expect(executed.size).toBeGreaterThan(10)` in the suite, so
  downgrading one route (15 tests to 14) also stays green.
- Annotating all 27 operations `x-pullfm-dast: exclude` produces `paths: {}` and
  `OK 0 operation(s) in the DAST-safe spec`, exit 0. ZAP would then import zero operations and
  report clean. The pruner's own header calls that "the worst possible outcome: a green DAST result
  that proves nothing", and the script has no floor preventing it.

Both need a minimum-count assertion, the same shape as the fix applied to F7.

#### F17. The BOLA coverage ledger is populated at collection time, not at run time

**Reasoned.** `apps/bff/test/security/bola.test.ts:481`.

`executed.add(row.route)` is the last statement of the `describe.each` callback body, which Vitest
runs during collection for every row. The reconciliation therefore sees a full set whether or not
any test executed. The comment claims it catches "a `.skip`, a name filter, or an exception that
truncates the loop"; it catches only the third. A `--testNamePattern` filter leaves it green.

The real backstop is the `toBeGreaterThan(10)` floor, which catches wholesale removal only. Moving
the `add` into the test body fixes it.

#### F18. Two unverified network fetches, one of them on every production node

**Proved by a subagent.**

- `infra/terraform/modules/compute/templates/cloud-init.yaml.tftpl:110` runs
  `curl -fsSL https://tailscale.com/install.sh | sh` on every provisioned node, unpinned. A
  compromise of that host or that TLS path is root on the application node at boot. Pin a version
  and verify a checksum, or install from the apt repository with a pinned key.
- `.github/workflows/security.yml` downloads the gitleaks binary from a GitHub release and
  `sudo install`s it with no checksum. The version is pinned, so this is tag-pinned but not
  content-pinned. Add `sha256sum -c`. The reasoning for running the CLI rather than the paid action
  is sound; only the verification is missing.

#### F19. `check-zap-fragments.mjs` and `prune-openapi.mjs` were wired to nothing

**Proved.** Cross-referenced every script under `security/` and `infra/scripts/` against all three
workflows, `package.json`, and the `Makefile`.

`security/zap/context/pullfm-api.context.yaml:8` states that `check-zap-fragments.mjs` "fails CI if
a copy drifts from this file", and `security/zap/rules/alert-filters.yaml:6` repeats it. It failed

**Fixed:** `check-zap-fragments.mjs` is now a step in `ci.yml`. `prune-openapi.mjs` still has no

### LOW

- **F20. `noeviction` does not produce the loud write error the design assumes.** _Proved._ Against
  a real `noeviction` instance at `maxmemory`: a 64 KB `SET` is refused with `OOM command not
allowed`, while `INCR`, `SET ... EX`, `SET NX` and the quota `EVAL` on new keys all keep
  succeeding, because Redis refuses the write that would exceed the limit rather than allowing
  memory to go over. The quota instance holds only small values, so in practice the limiter keeps
  working, which is the outcome we want. But `lib/redis.ts` reasons that "the failure mode is a loud
  write error instead", and that is true only for whichever write happens to be large enough. There
  is no alert here, in either direction. Worth a monitored `used_memory` ratio rather than relying on
  a write to fail.
- **F21. The rate limiter stops recording its own evidence after 20,000 dispatches.**
  `rate-limiter.ts:176` caps `#dispatchTimes`, and `peakInWindow` is the measurement Gate 1's
  "<= 1.0 req/s at the network layer" is argued from. A 10,000-request burst fits, so Gate 1 is
  safe today, but a longer run silently measures a prefix. Make it a ring buffer, or fail loudly at
  the cap.
- **F22. `DOCS_ENABLED` defaults to `true`.** `config.ts:250`. That serves a 3.75 MB inlined
  third-party SPA needing `unsafe-inline` and `unsafe-eval` on the API origin by default. The
  mitigations around it are genuinely careful and were verified: the bundle is inlined rather than
  fetched from jsdelivr, `withDefaultFonts: false`, and the CSP relaxation is scoped to `/docs` by a
  Fastify encapsulation context with `connect-src 'self'`, which blocks Scalar's default
  `proxy.scalar.com`. The finding is only the default: fail-open on a surface that widens CSP.
- **F23. Lifecycle scripts run during install.** No `.npmrc`, `ignore-scripts` unset, no
  `onlyBuiltDependencies` allowlist, and `packageManager: pnpm@9.12.0` (pnpm 9 runs dependency
  lifecycle scripts by default; the block-by-default behaviour arrived in pnpm 10). Today the only
  `postinstall` in the tree is `esbuild`, which is dev-only and absent from the Dockerfile's
  prod-filtered install, so current exposure is nil. The guard is absent, so a future dependency
  gains script execution silently. THREAT-MODEL M39 lists this as `partial` and is accurate.
- **F24. `retired` exempts an expired entry with no evidence requirement.** _Proved._ Flipping
  `status: accepted` to `retired` on an expired entry, changing nothing else, returns
  `OK 9 accepted risk(s) valid`. This is the documented escape hatch and it is reasonable, but it
  costs 20 characters of `review_notes` and no proof the issue was closed.
- **F25. The pinning lint counts floating tags as pinned.** `postgres:18-alpine` and `redis:7-alpine`
  are re-pushed tags and both count toward the reassuring "21 references pinned". It also reads only
  `.github/workflows` non-recursively, so a composite action at `.github/actions/*/action.yml`,
  which can contain its own `uses:`, is never scanned.
- **F26. `edoburu/pgbouncer:latest`** in `docker-compose.dev.yml:90`, while every sibling image is
  pinned. Dev only.
- **F27. Threat-model statuses are stale relative to shipped work.** `M40` still describes
  `security.yml` as using `@v4`, `@v2`, and `semgrep/semgrep:latest`, all since fixed and the risk
  retired. `M24` and `M25` are `spec` although both are implemented in `infra/staging/`. Neither is a
  vulnerability; both make the model less useful as a checklist.

## Threat model against the architecture that actually shipped

Three changes since the model was written. The register handles two of them well and misses the
third.

**The database moved to Neon and is reachable from the internet.** Well handled. `PULLFM-RISK-007`
is an honest entry: it states plainly that three independent network controls became zero and that
the credential is no longer the primary control but the only one. The compensating controls are real
and verifiable rather than aspirational, in particular the least-privilege `pullfm_app` role proved
by `verify-app-role.sql` to be unable to DROP, ALTER, CREATE, TRUNCATE, read `pg_authid`, or
`SET ROLE`. The pricing justification is specific enough to re-argue. My only addition: the entry's
review notes should also list "confirm the envelope is still the only thing between a leaked
connection string and A1", because F-nothing here weakens it, but it is now the last line rather
than the third.

**Terraform state holds plaintext production database passwords in R2, on an account-scoped
credential that also reaches backups.** Well handled, and `PULLFM-RISK-008` through `010` are the
strongest entries in the register. They were produced by probing the live bucket rather than reading
documentation, they corrected two of their own earlier claims, and `009` states outright that it is
a scoping mistake rather than a platform limitation and should not wait for its expiry. I have
nothing to add except agreement with `009`'s own recommendation: mint bucket-scoped tokens and then
re-prove the isolation by trying to violate it, because an isolation claim never tested by attacking
it is an assumption.

**The load balancer was removed and the origin answers 443 on its public interface.** This is the
gap. It is not in the register, it is not in the threat model, and the compensating control that the
nginx configuration says closes it does not close it. See F10. The three-layer argument in
`infra/staging/README.md` and `infra/terraform/README.md` reads as three independent controls and is
one control stated three times.

Two model updates that follow from the above, neither yet applied:

- `T01` should be re-rated with the observation that the origin bypass is currently unmitigated
  rather than mitigated by `M24`, and `M24`'s status is `spec` while the mTLS half is implemented.
- `T11` should gain a second instance covering the in-process limiter (F12). The model currently
  reasons about eviction only in Redis, which is the one place it is now handled correctly.

## What could not be assessed

- **DAST.** No target. `api-staging.pull.fm` resolves and terminates TLS at Cloudflare but answers
  **521**, meaning the edge is up and the origin is not. `docs/PROTOTYPE.md` does not exist. No ZAP
  run of any kind has ever executed in this project.
- **Observatory grade.** Requires a live origin. A grade measured against a Cloudflare 521 page
  would describe Cloudflare's error page. HSTS was not observable on that response, so whether the
  `security_header` zone setting is producing the intended header is also unconfirmed.
- **Origin security headers.** Helmet's CSP, HSTS, `nosniff`, and `Referrer-Policy` are configured
  in code and were not observed on the wire, for the same reason. Only `referrer-policy: same-origin`
  and `x-frame-options: SAMEORIGIN` came back, both from Cloudflare.
- **The deployed image.** All dependency findings describe this repository's lockfile. I did not
  scan `ghcr.io/312-dev/pull-fm/bff`, so I cannot say the running artifact matches.
- **Maintainer 2FA and npm provenance** for the single-maintainer direct dependencies (`jose`, `pg`,
  `zod`, `husky`). Not exposed by registry metadata. This is the largest remaining unknown for
  account-takeover risk in the supply chain.
- **Whether the F10 bypass works end to end.** I did not stand up a second Cloudflare zone pointed
  at the origin, both because the origin is down and because doing so against production
  infrastructure is not something to run unattended. The conclusion rests on Cloudflare's documented
  behaviour that the zone-level origin-pull certificate is shared across customers, which the
  repository's own configuration comment already states.
- **Whether the documentation sample token in `docs/api/personal-api-tokens.md` was ever a real
  issued token.** It is now allowlisted by value so the scan is clean either way. It has been in a
  public repository's history since `fe928f2`. If there is any chance it was minted rather than
  invented, revoke it; that is a one-minute check and the only reason it is listed here.
